# Change Request — Structured Today's Overview & Forecast for Tomorrow

## Purpose
Update the **General Information** tab of the Daily Reporting System. `Today's Overview` and `Forecast for Tomorrow` must no longer be entered as a single free-text/list field or pasted preformatted text. Provide structured inputs for each data point, then generate the report text from those values.

This is a change request to the existing Laravel 13 / PHP 8.3 / Livewire 4 / Tailwind CSS 4 / MySQL project. **Do not restart or rebuild the application.** Inspect the current code and project documentation first, then implement with minimal disruption.

## Example required output

### Today's Overview
- Occupancy: 20.00%
- Rooms Occupied: 15 Rooms
- Out of Order: 3 Rooms — #2310, #2321 & #3311 (Preventive Maintenance Program)
- Number of Guests: 33 Pax (31 Adults + 2 Children)
- Check-ins: 7 Rooms
- Check-outs: 7 Rooms
- Property Tours: Room #2311 & #4103
- Manager on Duty: Ariawan, Agung Janardana, Laksmi

### Forecast for Tomorrow
- Projected Occupancy: 16.00%
- Rooms Projected: 12 Rooms
- Out of Order: 3 Rooms — #2310, #2321 & #3311 (Preventive Maintenance Program)

The Forecast example is partial. Inspect existing documentation and the current template to identify additional forecast fields. Preserve all already documented fields and their ordering; do not invent data or silently remove requirements.

## Required behavior
1. Replace the single text/list entry experience for these two sections with structured fields.
2. User enters each value separately; labels are generated by the system.
3. Generate formatted report lines in the sample format.
4. Keep Today's Overview and Forecast for Tomorrow separate.
5. Preserve existing wizard flow, tab navigation, save behavior, draft/resume, hotel/date context, authorization, and design system.
6. Do not change other General Information fields or other tabs unless necessary.
7. Store structured data; do not store only the final formatted string.
8. Generated output must be consistently available for review/export/print while the underlying values remain editable.

## Suggested fields — Today's Overview

| Field | Input | Notes |
|---|---|---|
| Occupancy | Decimal percentage | Example 20.00 |
| Rooms Occupied | Integer | Append `Rooms` in output |
| Out of Order — room numbers | Multi-value room list | Example 2310, 2321, 3311 |
| Out of Order — reason | Text | Example Preventive Maintenance Program |
| Number of Guests — adults | Integer | Example 31 |
| Number of Guests — children | Integer | Example 2 |
| Number of Guests — total | Derived where feasible | Prefer Adults + Children = total (33) to prevent inconsistency |
| Check-ins | Integer | Append `Rooms` |
| Check-outs | Integer | Append `Rooms` |
| Property Tours | Multi-value room list | Example 2311, 4103 |
| Manager on Duty | Multi-value names or text | Example Ariawan, Agung Janardana, Laksmi |

Prefer deriving OOO count from the room-number list rather than storing a separately editable count that could disagree. If architecture requires a separate count, validate consistency.

## Formatting and validation
- Occupancy percentages: numeric, 0–100 unless project specifications say otherwise.
- Counts: non-negative integers.
- Guest total: preferably calculate from Adults + Children; if not, validate consistency and explain the decision.
- Room identifiers: store raw values (without `#`), display with `#` in output.
- Room-list formatting: use commas and `&` before the final item, e.g. `#2310, #2321 & #3311`.
- Property Tours: format room identifiers consistently and handle singular/plural naturally.
- Manager on Duty: trim empty entries and join with comma-space.
- Omit optional empty fields/lines. Never produce misleading output such as `Out of Order: 0 Rooms — (reason)` when no OOO rooms exist.
- Guest Experience remains a paragraph field and must not be affected by list normalization.

## Suggested fields — Forecast for Tomorrow
At minimum, based on the example:
- Projected Occupancy (percentage, example 16.00%)
- Rooms Projected (integer, output with `Rooms`)
- Out of Order room numbers (multi-value; example 2310, 2321, 3311)
- Out of Order reason (optional text; example Preventive Maintenance Program)

Inspect the existing approved template/specification for additional Forecast fields. Do not remove existing documented fields. Keep output order consistent with the approved template.
